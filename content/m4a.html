Part 3 ended with a question the copilot could not answer: "Who supplies the windshield glass?" The answer sits in the part master, not in a document. In this part you give the model tools, then let it use them in a loop. That is what people mean by agentic AI.

What tool calling is, precisely

You send the model a list of tools, each with a name, a description and a JSON schema for its parameters. When the model decides a tool would help, it does not run anything. It replies with a structured request: "call get_part with part_no = E3-4200". Your code runs the function, and sends the result back as a new message. The model then answers, or asks for another tool.

user:       Who supplies the windshield glass?
assistant:  [tool call] search_parts(text="windshield glass")
tool:       [{"part_no": "E3-4200", "description": "Windshield glass", ...}]
assistant:  [tool call] get_part(part_no="E3-4200")
tool:       {"part_no": "E3-4200", "supplier": "ClearView Glass", ...}
assistant:  The windshield glass E3-4200 is supplied by ClearView Glass.

This split is the most important safety property of agents: the model only proposes actions; your code decides whether and how they run. Every guard rail you will build sits in that gap.

Why tools beat bigger prompts

  • Exact data. A query returns the real supplier, the real stock and the real quantity, with no chance of the model misreading a long table.
  • Current data. Tools read the system of record at the moment of the question.
  • Arithmetic done by code. "How many E3-9001 bolts per vehicle?" needs a BOM roll-up. A tool computes it; the model would guess.
  • Access control. The tool runs with the user's rights, so it returns only what the user may see.
  • Actions. Tools can also create, update and send things. That is where the risk is, and Unit 16 is about controlling it.

Designing good tools

The model chooses tools based only on their names, descriptions and parameter schemas. Tool design is therefore prompt design.

Which models can call tools

Tool use is trained into a model. All major cloud models support it. Among open models, look for the "tools" tag on Ollama: Qwen 2.5 and later, Llama 3.1 and later, Mistral and others. Small models call tools reasonably for simple, well-described tools and get worse with many steps. You will see this, and it is a useful thing to have seen before you advise customers.

Step 2: the tools module

%%writefile plmtools.py
"""Read-only PLM tools over the Sahyadri synthetic data.
Used by the agent in Part 4 and the MCP servers in Part 5."""
import pandas as pd

BUILD_RATE_PER_MONTH = 1500
PARTS = pd.read_csv("parts.csv").fillna("")
EBOM = pd.read_csv("ebom.csv").fillna("")
CHANGES = pd.read_csv("changes.csv").fillna("")


def _clean(part_no):
    return str(part_no).strip().upper()


def _description(part_no):
    row = PARTS[PARTS.part_no == part_no]
    return row.description.iloc[0] if len(row) else ""


def search_parts(text: str, limit: int = 5) -> list:
    """Find parts whose description contains the words in text."""
    words = [w for w in text.lower().split() if len(w) > 2]
    desc = PARTS.description.str.lower()
    hits = PARTS[desc.apply(lambda d: all(w in d for w in words))]
    if hits.empty:
        hits = PARTS[desc.apply(lambda d: any(w in d for w in words))]
    return hits.head(limit)[["part_no", "description", "rev", "lifecycle"]].to_dict("records")


def get_part(part_no: str) -> dict:
    """Return the part master record for one part."""
    row = PARTS[PARTS.part_no == _clean(part_no)]
    if row.empty:
        return {"error": f"No part {part_no} in the part master. Use search_parts to find the number."}
    rec = row.iloc[0].to_dict()
    return {k: (v.item() if hasattr(v, "item") else v) for k, v in rec.items()}


def where_used(part_no: str) -> list:
    """List the assemblies that directly contain a part, with quantity per assembly."""
    rows = EBOM[EBOM.part_no == _clean(part_no)]
    if rows.empty:
        return [{"error": f"{part_no} is not used in the E3 engineering BOM."}]
    return [{"parent": r.parent, "parent_description": _description(r.parent), "qty_per_parent": int(r.qty)}
            for r in rows.itertuples()]


def qty_per_vehicle(part_no: str) -> dict:
    """Total quantity of a part in one vehicle, rolled up through every BOM level."""
    part_no = _clean(part_no)
    rows = EBOM[EBOM.part_no == part_no]
    if rows.empty:
        return {"error": f"{part_no} is not used in the E3 engineering BOM."}
    total = 0
    for r in rows.itertuples():
        qty, parent = int(r.qty), r.parent
        while parent:
            up = EBOM[EBOM.part_no == parent].iloc[0]
            qty, parent = qty * int(up.qty), up.parent
        total += qty
    return {"part_no": part_no, "qty_per_vehicle": total}


def list_changes(part_no: str = "", status: str = "") -> list:
    """List engineering changes, optionally only those affecting a part or with a given status."""
    df = CHANGES
    if part_no:
        df = df[df.affected_parts.str.split(";").apply(lambda ps: _clean(part_no) in ps)]
    if status:
        df = df[df.status.str.lower() == status.lower()]
    return df.to_dict("records")


def stock_exposure(part_no: str) -> dict:
    """Stock of a part at Chakan, its value, and how many months of production it covers."""
    part = get_part(part_no)
    if "error" in part:
        return part
    per_vehicle = qty_per_vehicle(part_no).get("qty_per_vehicle", 0)
    stock, cost = int(part["stock_chakan"]), float(part["unit_cost_inr"] or 0)
    months = round(stock / (per_vehicle * BUILD_RATE_PER_MONTH), 1) if per_vehicle else None
    return {"part_no": part["part_no"], "stock": stock, "unit_cost_inr": cost,
            "stock_value_inr": round(stock * cost), "qty_per_vehicle": per_vehicle, "months_of_stock": months}


def _spec(name, description, params, required=()):
    return {"type": "function", "function": {"name": name, "description": description,
            "parameters": {"type": "object", "properties": params, "required": list(required)}}}

PART = {"type": "string", "description": "Part number, for example E3-2400"}
TOOL_SPECS = [
    _spec("search_parts", "Find part numbers from a description such as 'windshield glass'. "
          "Use this first when the user names a part but gives no number.",
          {"text": {"type": "string", "description": "Words from the part description"}}, ["text"]),
    _spec("get_part", "Get the part master record: revision, lifecycle, make or buy, material, "
          "mass, unit cost, supplier and stock.", {"part_no": PART}, ["part_no"]),
    _spec("where_used", "List the assemblies that directly contain a part, with quantity per assembly. "
          "Use for impact questions.", {"part_no": PART}, ["part_no"]),
    _spec("qty_per_vehicle", "Total quantity of a part in one vehicle across all BOM levels.",
          {"part_no": PART}, ["part_no"]),
    _spec("list_changes", "List engineering changes (ECN or ECR), optionally for one part or one status "
          "(new, draft, in review, released).",
          {"part_no": PART, "status": {"type": "string", "description": "Optional status filter"}}),
    _spec("stock_exposure", "Stock of a part at Chakan, its value in rupees, and months of production it covers.",
          {"part_no": PART}, ["part_no"]),
]
TOOLS = {"search_parts": search_parts, "get_part": get_part, "where_used": where_used,
         "qty_per_vehicle": qty_per_vehicle, "list_changes": list_changes, "stock_exposure": stock_exposure}

Read it carefully. Every function returns small, plain records or an error message that tells the model what to do next. Every arithmetic step (roll-up, stock value, months of stock) is in code. The schemas at the bottom are what the model sees.

An agent is less mysterious than its marketing. It is a model, a set of tools and a loop. This session explains the loop, what makes it go wrong, and when you should not build one at all.

The loop

messages = [system prompt, user request]
repeat up to N times:
    reply = model(messages, tools)
    if reply has no tool calls:
        return reply.text                  # the agent has finished
    for each tool call in reply:
        result = run the tool (if allowed)
        append the result to messages      # the agent "observes"
stop: too many steps, ask a person

This pattern is often called ReAct: the model reasons about what it needs, acts by calling a tool, observes the result, and repeats. The conversation history is the agent's working memory: every tool result stays in it, so the model can build on earlier steps.

What the loop gives you

  • Flexible paths. For "what is the impact of changing E3-9001?", the agent can discover that the bolt is used in two assemblies, then check each, then look for open changes, without you coding that path.
  • Self-correction. A tool error ("no part E3-240") comes back as an observation, and the model can try again.
  • Combining sources. Documents (search) and structured data (part master, BOM) in one answer.

What goes wrong

Workflow or agent?

A workflow is a path you define in code, with model calls at some steps. An agent chooses its own path. Anthropic's advice, which matches industrial experience, is to use the simplest thing that works: a single model call, then a fixed workflow, and an agent only when the steps genuinely cannot be known in advance.

WorkflowAgent
PathFixed in codeChosen by the model at run time
Predictability and auditHighLower; needs traces

Engineering exampleStandard change impact report"Why did warranty claims for lighting rise last quarter?"

Most good industrial systems are hybrids: a workflow for the known steps, with an agent inside one step where open investigation is needed.

Traces are your inspection record

Log every step: the model's request, the tool, the arguments, the result and the time. Traces are how you debug, evaluate and audit agents. In Part 6 they become the logs you monitor in production.

Step 2: the loop

SYSTEM = """You are a PLM analyst assistant at Sahyadri Motors.
Use the tools to look up facts. Never invent part numbers, quantities, suppliers or values:
every number in your answer must come from a tool result.
If you cannot find something, say so. Keep the final answer short and list the part numbers you used."""

def run_tool(name, args, tools):
    if name not in tools:
        return {"error": f"Unknown tool {name}. Available: {sorted(tools)}"}
    try:
        return tools[name](**args)
    except TypeError as e:
        return {"error": f"Bad arguments for {name}: {e}"}

def run_agent(task, specs=TOOL_SPECS, tools=TOOLS, max_steps=6, verbose=True):
    messages = [{"role": "system", "content": SYSTEM}, {"role": "user", "content": task}]
    trace, seen = [], set()
    for step in range(1, max_steps + 1):
        r = ollama.chat(model=MODEL, messages=messages, tools=specs, options={"temperature": 0})
        messages.append(r.message)
        calls = r.message.tool_calls or []
        if not calls:
            if verbose:
                print(f"[{step}] answer")
            return {"answer": r.message.content, "trace": trace, "steps": step}
        for call in calls:
            name, args = call.function.name, dict(call.function.arguments)
            key = (name, json.dumps(args, sort_keys=True))
            if key in seen:
                result = {"error": "You already called this tool with these arguments. Use the earlier result."}
            else:
                result = run_tool(name, args, tools)
                seen.add(key)
            trace.append({"step": step, "tool": name, "args": args, "result": result})
            if verbose:
                print(f"[{step}] {name}({args}) -> {json.dumps(result, default=str)[:160]}")
            messages.append({"role": "tool", "tool_name": name, "content": json.dumps(result, default=str)})
    return {"answer": "Stopped: step limit reached. A person should review the trace.", "trace": trace, "steps": max_steps}

Read it line by line. The loop ends when the model replies without tool calls. Unknown tools, bad arguments and repeated calls return errors as observations, never exceptions. The step limit stops runaway loops. The trace records everything.

Godavari Foods wants an agent. Your job is to decide what kind of system they actually need, and to show the cost and reliability arithmetic.

The situation

Sunita Patil, plant head at Godavari Foods in Nashik, liked the predictive maintenance pilot from Part 2. Now she wants "an AI agent that handles maintenance". Each day the plant raises about 40 maintenance requests from operators, by phone and on paper. A planner reads each, finds the machine and its history, checks spare stock, sets a priority and creates a work order in SAP PM. It takes about 12 minutes per request.

About 85% of requests are routine (known machine, known fault, standard job plan). About 15% are unclear ("line 3 sounds strange", "seals keep failing") and need investigation of history and manuals.

Two proposals:

  • A. Free agent. One agent with 12 tools handles every request end to end. Measured in a trial: 78% of requests handled correctly, on average 9 model calls each, about 40 seconds each.
  • B. Workflow with an agent inside. A fixed workflow extracts the request, looks up the machine and history, matches a job plan and drafts the work order for one-click planner approval. Only the unclear 15% go to an investigation agent, which drafts a summary for the planner. Measured: routine requests 95% correct with 2 model calls; unclear requests 70% useful.

Your questions

  1. Compare the expected number of correctly handled requests per day for A and B.
  2. Compare model calls per day.
  3. Which would you recommend, and how would you explain the choice to Sunita in two sentences?
  4. What must stay with the planner in either design?
Model answer

1. A: 40 × 78% ≈ 31 correct. B: routine 34 × 95% ≈ 32.3, unclear 6 × 70% ≈ 4.2, about 36.5 correct or useful. B handles about 5 more requests a day well.

2. A: 40 × 9 = 360 calls. B: 34 × 2 + 6 × 9 = 68 + 54 = 122 calls, about a third. B is also faster and more predictable for routine requests.

3. B. "Most of your requests follow a known procedure, so we automate that procedure step by step, which is more reliable and easy to audit. The agent's flexible investigation is used only for the unclear 15%, where it adds the most value."

4. Approval of every work order and its priority, decisions to stop a line, and any safety-related job. The system drafts; the planner decides. Over time, the most reliable routine categories could move to automatic creation with spot checks, based on measured accuracy.

What the case teaches. "Agent" is a design choice, not a product category. Use code for the known path and an agent where the path is unknown; it is usually cheaper, faster and more reliable.

Six questions on agent loops, then trace-reading practice.

The agent loop ends normally when:

  1. The model replies without any tool calls
  2. Every tool has been called once
  3. The temperature reaches zero
  4. The user closes the window

No tool calls means the model has given its answer.

Why return tool errors as observations instead of raising exceptions?

  1. Exceptions are slow
  2. To hide bugs
  3. So the model can correct itself and the loop keeps running
  4. Ollama requires it

Errors are information for the agent.

In the Godavari case, design B was better mainly because:

  1. It used a bigger model
  2. It had more tools
  3. It had no human approval
  4. It used code for the routine 85% and an agent only for the unclear 15%

Match the design to how predictable the work is.

Why do agent costs grow faster than the number of steps?

  1. Tools charge per call
  2. Each step resends the growing history, including all earlier tool results
  3. Models get slower with time
  4. They do not

Compact tool results and step limits control it.

A trace is:

  1. A record of every model request, tool call, argument and result in a run
  2. The final answer
  3. The system prompt
  4. A chart of token use

It is the agent's inspection record.
