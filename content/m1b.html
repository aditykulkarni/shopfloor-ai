Almost every question that crosses two systems is a join. This session teaches the four joins and the five ways data goes wrong, so you can read any reconciliation report and know what it means.

The four joins

A join matches rows in two tables on a key. Picture the EBOM on the left and the MBOM on the right, matched on part number.

JoinKeepsAnswers
InnerOnly parts in both"For parts both sides know, do quantities agree?"
LeftEvery EBOM part, with MBOM data where it exists"Has every engineered part been planned?"
RightEvery MBOM part, with EBOM data where it exists"Is everything the plant builds backed by engineering?"
OuterEvery part from either side"Show me all differences at once."

For a reconciliation you want the outer join, plus a marker saying where each row came from. pandas gives you that marker with indicator=True: left_only, right_only or both.

Joins that silently go wrong

  • Key format differences. "E3-1100" and "E3-1100 " (trailing space) do not match. Neither do "e3-1100" or "E31100". Always clean keys before joining.
  • Duplicate keys. If a part appears three times on the left and twice on the right, an inner join produces six rows. Summarise to one row per key first, or include enough columns in the key.
  • Revision mismatch. Joining on part number alone matches revision B in engineering with revision A in manufacturing. The join "succeeds" and hides the problem.

Five dimensions of data quality

DimensionQuestionBOM example
CompletenessIs anything missing?An EBOM part with no MBOM line
AccuracyIs the value right?24 cells per module in engineering, 20 in manufacturing
ConsistencyDo two systems agree?Descriptions differ between PLM and ERP
TimelinessIs it current?The MBOM still points at last year's revision
ValidityDoes it obey the rules?A quantity of zero, a parent that does not exist

These five words let you turn "the data is bad" into a list of specific, fixable findings with owners. That list is what a customer's management will act on.

Why AI cares so much

A model learns whatever patterns are in its training data, including the errors. If 10% of labels are wrong, the model's ceiling is roughly 90% agreement with reality, however clever it is. Generative AI has the same problem in a different form: a copilot that answers from outdated work instructions gives confident, outdated answers.

The roll-up, done properly

Quantity per vehicle is the product of quantities along the path from the top, summed over every path. A bolt used 16 times in the frame and 8 times in the powertrain is 24 per vehicle; a cell used 24 times per module and 4 modules per pack is 96. The clean way to compute this is to explode the BOM: start at the top, walk down every line, multiply as you go and record each line's quantity per vehicle. Then sum by part.

%%writefile bomcheck.py
"""BOM health checker: compare an EBOM and an MBOM and report every mismatch."""
import sys
import pandas as pd

PLANT_PREFIXES = ("C-", "M-")   # consumables and kits that only exist in the MBOM


def load_bom(path):
    bom = pd.read_csv(path, keep_default_na=False)
    required = {"part_no", "description", "parent", "qty"}
    missing = required - set(bom.columns)
    if missing:
        raise ValueError(f"{path} is missing columns: {sorted(missing)}")
    bom["part_no"] = bom["part_no"].astype(str).str.strip().str.upper()
    bom["parent"] = bom["parent"].astype(str).str.strip().str.upper()
    return bom


def explode(bom, root, mult=1, level=1, out=None):
    """Walk down from root; one row per line with its quantity per top unit."""
    if out is None:
        out = []
    for _, line in bom[bom["parent"] == root].iterrows():
        per_unit = mult * line["qty"]
        out.append({"part_no": line["part_no"], "description": line["description"],
                    "level": level, "qty_per_unit": per_unit})
        explode(bom, line["part_no"], per_unit, level + 1, out)
    return pd.DataFrame(out)


def rolled_up(bom):
    root = bom.loc[bom["parent"] == "", "part_no"].iloc[0]
    lines = explode(bom, root)
    return lines.groupby("part_no", as_index=False).agg(
        description=("description", "first"), qty=("qty_per_unit", "sum"))


def compare(ebom, mbom):
    e, m = rolled_up(ebom), rolled_up(mbom)
    cmp = e.merge(m, on="part_no", how="outer", suffixes=("_ebom", "_mbom"), indicator=True)

    def classify(r):
        if r["_merge"] == "left_only":
            return "missing in MBOM"
        if r["_merge"] == "right_only":
            return "plant item" if r["part_no"].startswith(PLANT_PREFIXES) else "not in EBOM"
        return "ok" if r["qty_ebom"] == r["qty_mbom"] else "quantity mismatch"

    cmp["status"] = cmp.apply(classify, axis=1)
    cmp["description"] = cmp["description_ebom"].fillna(cmp["description_mbom"])
    return cmp[["part_no", "description", "qty_ebom", "qty_mbom", "status"]].sort_values(["status", "part_no"])


def orphans(bom):
    """Lines whose parent does not exist as a part in the same BOM."""
    known = set(bom["part_no"])
    return bom[(bom["parent"] != "") & (~bom["parent"].isin(known))]


if __name__ == "__main__":
    if len(sys.argv) == 3:
        ebom_path, mbom_path = sys.argv[1], sys.argv[2]
    else:
        ebom_path, mbom_path = "ebom.csv", "mbom.csv"
    ebom, mbom = load_bom(ebom_path), load_bom(mbom_path)
    report = compare(ebom, mbom)
    issues = report[~report["status"].isin(["ok", "plant item"])]
    print(report["status"].value_counts().to_string())
    print()
    print(issues.to_string(index=False))
    print(f"\nOrphan lines in MBOM: {len(orphans(mbom))}")
    with pd.ExcelWriter("bom_report.xlsx") as xl:
        issues.to_excel(xl, sheet_name="issues", index=False)
        report.to_excel(xl, sheet_name="all parts", index=False)
    print("Saved bom_report.xlsx")
